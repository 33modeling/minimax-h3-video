# Ref2VA 추가 개선 검토 · 2026-11-04

검토한 실행 소스는 `7b705452056e93f55ed07a9ef94d64ac2919bd9d`다. 추가 결함 두 건을 CPU에서 대조 재현했다. 이번 변경은 감사 기록이며 실행 코드를 수정하지 않았다. 사용자 H100의 실제 오류 단계와 이 결함의 일치는 확인하지 못했다.

## 먼저 처리할 결함

### 1. 원본 픽셀을 worker마다 다시 보내는 비용 제거

`src/h3video/dserver.py:404`의 `_denoise_remote`는 denoiser 입력·분기 키를 보존한다. 설치된 Diffusers 0.41.0의 `MiniMaxH3AutoDenoiseStep`은 `references`와 `normalized_references`를 모두 포함하므로 원본과 전처리 프레임 배열도 전송된다. `dworker.py:128`은 같은 바이트를 모든 rank에 배포하고 각각 역직렬화한다. 주석에 적힌 원본 영상 제거는 이 경로에서 이루어지지 않는다.

24×128×128 RGB 합성 배열 두 개를 실제 `_denoise_remote`에 넣었다. 배열은 각각 1,179,648바이트이고 전체 요청은 **2,367,201바이트**였다. 캡처한 요청을 읽어 두 배열이 그대로 존재하는 것을 확인했다. 이 재현은 CPU 직렬화 검사다. GPU VRAM 증가나 사용자 OOM의 원인을 측정한 결과가 아니다.

조건 잠재값을 만든 뒤 worker에는 분기·모달리티 메타데이터와 필요한 텐서만 보내는 방안을 검토한다. 설치된 `before_denoise.py`의 Ref2VA 레이아웃은 모달리티와 잠재값 모양을 사용하지만, 모든 분기와 버전에서 원본 데이터가 불필요한지는 별도 검증해야 한다. 메타데이터로만 바꾼 예시의 7,521바이트는 **크기 비교**이며 호환성이나 동일 출력을 검증한 구현이 아니다.

현황판 [#1208](https://77model.pages.dev/bug-board/#item=1208), H3-034. 미수정.

### 2. worker가 죽어도 OOM 상세 기록 보존

`src/h3video/dworker.py:154`는 오류 결과를 만들지만 메모리 오류이면 163행에서 다시 예외를 발생시킨다. 응답은 174행에서 보내므로 이 경우 구조화한 오류 결과가 부모에게 도달하지 않는다. stderr traceback은 남는다.

실제 요청의 try/finally와 후속 응답 코드를 AST로 추출하고 계산만 실패하는 모의 pipe로 대조했다. 일반 오류는 DONE 메시지 1회, CUDA OOM 문구 오류는 정리·finally를 거친 뒤 DONE 메시지 **0회**였다. 전체 worker·분산 통신 검증은 아니다.

요청 ID·rank·단계·장치·오류·해당 프로세스의 메모리 최고치를 원자적으로 기록하고 부모가 회수하도록 개선한다. 이미 한 rank가 죽은 상태에서 새 집합 통신을 기다리게 만들면 안 된다. 부모 프로세스의 CUDA allocator 값은 다른 worker 프로세스의 할당량을 대신하지 못한다.

현황판 [#1209](https://77model.pages.dev/bug-board/#item=1209), H3-035. 미수정.

## 이어서 개선할 경로

| 우선순위 | 개선 | 현재 근거와 검증 조건 |
|---|---|---|
| 높음 | 실패 단계별 재시도 | `dserver.py:829`는 메모리 오류와 WorkerDied에 같은 축소·재적재 절차를 적용한다. 이미 host RAM으로 분류된 오류는 재시도하지 않는다. 모델 적재·텍스트 인코딩·VAE·denoising·일반 worker 종료를 나누고, 크기를 줄여 회복 가능한 경우에만 재시도해야 한다. |
| 높음 | 재시도에서 준비 결과 재사용 | `_run`은 매번 `_load_inputs`와 `_prepare_prompt`를 실행한다. 재시도에서도 영상 읽기와 모델 기반 프롬프트 다듬기를 반복한다. 확정 프롬프트를 먼저 재사용하고 입력 캐시는 파일 해시·seed·모델·geometry를 구분하며 크기를 제한해야 한다. 실패한 CUDA 텐서를 보관하는 캐시는 피한다. |
| 높음 | 조건 GPU의 단독 최고 메모리 대응 | 현재 4장·8장 모두 텍스트 인코더·VAE 경로는 한 GPU다. 직전 수정은 컴포넌트 동시 상주를 줄였지만 텍스트 모델 하나의 활성값이 한 장에 들어간다는 실측은 없다. 실제 단계 최고치를 수집한 뒤 지원되는 모델 분산 또는 세부 오프로딩을 비교한다. 다른 모델의 TP 지원을 H3 텍스트 인코더 지원으로 간주하지 않는다. |
| 중간 | 준비·응답의 무진척 제한 시간 | `_wait_workers`와 `_recv`는 프로세스가 살아 있으면 계속 기다린다. ticker가 step 0을 반복하는 연결과 실제 단계 진척을 구분해야 한다. 단계별 제한 시간·원인 기록·자기 worker 그룹만 정리하는 경로를 검증한다. |

CPU 오프로딩과 여러 GPU 배치는 모델과 전송 비용에 따라 조정해야 한다. GPU 수만 늘리거나 다른 모델의 설정을 복사하는 것으로 충분 조건을 삼지 않는다. [Diffusers 공식 메모리 문서](https://huggingface.co/docs/diffusers/main/en/optimization/memory).

진단·재현성도 함께 보강할 필요가 있다. `diagnose.sh`는 최신 serve 로그 한 개를 선택하고 Diffusers 모델 검사는 fl2va만 지정한다. Ref 로그·worker별 기록·실행 SHA·실제 GPU 배치·입력 정보·단계별 최고 메모리를 한 묶음으로 저장해야 한다. `Server.save`는 plan을 제외하므로 비밀값을 뺀 실행 계획과 파일 해시를 별도 보존해야 중단된 요청을 같은 조건으로 재현하기 쉽다.
